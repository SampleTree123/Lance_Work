# 分阶段媒体规格：ViT / VAE 形状与预算示例

日期：2026-10-23。Technical owner：[训练接入](../training_integration.md)。关联[总方案](datamake_vae_references_branch_plan_20261022.md)。状态：用户提出按阶段/任务定义输入规格，本文给出代码核对和CPU算术示例；具体帧数、尺寸和效果未确认、未实施。没有运行模型、修改训练配置或执行消融。

## 1. 本轮提议与判断

用户建议：生成阶段的当前source ViT和历史ViT使用相同低规格；理解阶段只看候选视频ViT和prompt，不看source/target VAE或参考，尽量保留标准ViT；参考图片/视频分别定义VAE规格。用任务规格表达架构，而不是以某个统一全量输入为基准层层“压缩”。

此配置组织方式合理：同一冻结ViT/VAE可以按阶段与媒体角色采用不同预处理规格，不必新增编码器或先计算高规格特征再压缩。降低分辨率/帧数仍有信息损失；命名为规格不代表无损。

当前source ViT直接帮助理解本轮source内容，历史ViT提供旧版本上下文；二者可以共享采样与尺寸配置，但不能抹掉source身份和历史节点标签。source VAE保留细节，不足以证明source ViT可任意降低而不影响语义定位；“生成ViT价值较低”是待验证假设。

该提议扩展了前一次只调整早期历史的讨论范围。旧H0/H1/H2实验仍固定直接source规格来隔离早期历史作用；若新方案统一降低source ViT，这会成为新的候选基线，不能把两项同时改变后的差异全部归因于历史压缩。

## 2. 当前代码依据与形状约定

核对日期2026-10-23，官方4baeee0＋当前DataMake补丁：

- ViT：patch14、temporal patch2、spatial merge2，主干有效网格为ceil(F/2) × H/28 × W/28。Qwen记录的patch网格在merge之前，空间维是H/14、W/14；不可把两者混为一谈。
- 当前Wan2.2 VAE：时间4倍、空间16倍，48个latent通道。`scripts/datamake_runtime.py`明确传`latent_patch_size=(1,1,1)`，不是config_factory默认(1,2,2)。因此本例一个VAE latent网格单元对应一个主干token。
- 当前主干hidden_size=2048。VAE原始token为48维，经vae2llm投影为2048维；48不是序列长度。ViT输出经现有连接通路也对齐2048维。
- 本文视频尺寸按H×W书写；像素/latent张量使用[C,T,H,W]且省略batch维。loader可能转置存储，语义形状不变。
- 参考图片每张T=1独立编码；不能把不同视角当连续帧。参考视频是时序数据，按合法4k+1帧处理。

公式（处理后的合法尺寸）：

```text
L_vit = ceil(F/2) × (H/28) × (W/28)
Z_vae shape = [48, 1+(F-1)/4, H/16, W/16]  # F=4k+1
L_vae = (1+(F-1)/4) × (H/16) × (W/16)
主干表示 shape = [L, 2048]
```

## 3. 一套说明性规格，尚未冻结

例子：同一约5秒视频时间范围，第5次编辑之前已有5个节点，生成所选路径也恰有5个视频（含直接source）。候选节点数与路径节点数通常不同，本例设为相同仅便于算术。

| 阶段/角色 | 处理后像素输入 | 编码结果 | 每份主干token |
| --- | --- | --- | ---: |
| 理解：每个候选ViT | [3,62,336,588]，61采样帧＋复制末帧 | patch网格[31,24,42]；merge后有效网格[31,12,21]；[7812,2048] | 7812 |
| 生成：每个历史及source ViT（统一低规格提议） | [3,8,224,392]，8帧覆盖完整时间范围 | patch网格[4,16,28]；merge后[4,8,14]；[448,2048] | 448 |
| 生成：source VAE | [3,61,352,624] | [48,16,22,39] → [13728,2048] | 13728 |
| 生成：target VAE/噪声 | [3,61,352,624]是对应输出尺寸 | latent [48,16,22,39] → [13728,2048] | 13728 |
| 生成：每张方形参考图VAE | [3,1,512,512] | [48,1,32,32] → [1024,2048] | 1024 |
| 生成：动作参考VAE | [3,61,256,448] | [48,16,16,28] → [7168,2048] | 7168 |

target训练时是真值编码后加噪；推理时初始化对应shape的噪声，不读取目标真值视频。本例动作参考先保留与source相同时间采样、降低空间尺寸，优先保护节奏；只是候选配方，不把它设为用户最终决定。

更稀疏动作参考如33帧256×448，VAE为[48,9,16,28]、4032 token；必须覆盖同一时间窗，保留正确时间间隔，不能将33帧当12fps缩短动作时长。此选项尚未选定，快速动作可能受损。当前位置代码存在固定second_per_grid_ts口径，不能宣称仅改抽帧即可正确处理全部时间关系。

方形512²图片只是形状示例；非方形素材应按像素预算等比缩放/受控裁剪与16对齐，不统一强拉伸成方形。ViT用28对齐。source和target共享时间与输出几何合同，参考可以有独立尺寸。物理时间范围不等于采样帧数；8帧历史不是8帧时长。

## 4. 理解阶段预算

理解输入为所有候选节点ID、parent关系、历史与当前prompt、工具说明、候选ViT；没有source/target VAE或参考像素。是否保留参考角色元信息另按选择任务决定，不能自动加载参考视觉。

```text
L_und = N_candidates × 7812 + L_text_and_tool_schema
```

| 候选数 | 视觉token | 按现行65536预算衡量 |
| --- | ---: | --- |
| 5 | 39060 | 留有26476给文字/工具/边界与输出；长度可行不等于显存已测 |
| 6 | 46872 | 留有18664 |
| 8 | 62496 | 仅余3040，需精确统计文字及预留输出 |
| 9 | 70308 | 视觉部分已超预算 |

若全会话最多5次编辑，第5次生成前最多5个已有节点；完成5次后共6个节点。若只限制每条分支深度，候选总数可能更多，不能使用5或6作为全树上界。

这里“完整/标准ViT”指保留当前配置的采样与尺寸，不是原视频全部帧/像素。例子：同样336×588但150帧，每份18900 token，5份94500；可见读原始30fps视频的所有帧与标准61帧不是同一预算。

65536是现行生成训练profile/packer预算，本例暂以同一数值衡量理解输入，不称为官方统一上限或已实现的选择器配置。纯理解训练入口仍待接入；候选数、文字长度、输出预留、显存与位置范围需独立预检。

## 5. 生成阶段预算

统一低规格ViT本例中每份448 token，5份共2240。source/target VAE共27456：

```text
L_gen = L_text + 2240 + 27456 + L_current_refs_vae
```

| 当前任务 | 视觉token合计 |
| --- | ---: |
| 无参考的镜头/发色等编辑 | 29696 |
| 双图发型/服装参考（两张512²） | 31744 |
| 整套服装示例（八张512²） | 37888 |
| 动作参考（61帧256×448） | 36864 |
| 动作更稀疏候选（33帧256×448，未选定） | 33728 |

均未含文字、标记和pack对齐。服装图与动作视频按不同任务算，不默认同轮累加；历史参考不重复输入。理解与生成先后调用，两个长度不相加成一次forward。它们仍各自有编码/主干耗时，不能将两阶段总耗时等同生成一次；两阶段KV也不能直接互用。

## 6. 配置与实现建议

建议定义三个编码规格族和两类VAE角色，不冻结当前数字：

```text
selector_video_vit       # 标准规格，全部候选；文字与输出另预留预算
generator_video_vit     # 低规格，选中路径全部视频含source；节点角色保持
reference_image_vae     # 独立单图预算；按属性/部件/视角组织
reference_video_vae     # 动作时间窗、采样、分辨率
source_target_vae       # 生成尺寸与paired采样合同
```

同一个视频可以按两种ViT规格分别编码，也可以在同一解码结果上重采样；不需要两个ViT模型。不能直接把标准ViT输出池化为低规格特征并宣称与低分辨率重新编码等价。缓存应绑定冻结编码器版本、帧索引/时间窗、变换与尺寸；训练中的可变connector/主干表示不能当成永久固定编码缓存。

实现需要分角色预处理字段、真实pack预算、时间/网格元数据、训练推理一致性及独立理解入口。当前代码没有完成这套规格，表格也不是已运行配置。

## 7. 后续选择与原消融边界

本轮只讨论：是否采用生成source/history统一低规格、理解标准规格的方向，以及候选数上界。8帧224×392、61帧336×588、512²、61帧256×448均为例子，用户未最终确认。

历史ViT和历史prompt消融按此前决定暂不执行。低规格source ViT带来的目标定位风险需单独验证，不能预先断言所有生成ViT不重要。历史只需辨认大范围属性时较低规格可能足够，细小饰品/面部/短暂动作可能不足。

本轮代码读取和标准库算术核对完成，无GPU测量、无学习质量证据。之前文档中的历史ViT先保留高空间分辨率是候选建议，由本轮统一规格讨论重新评估，不能当作已接受约束。


## 8. 2026-10-23补充：官方分辨率桶、输出尺寸与长视频

已核对当日[官方README](https://github.com/bytedance/Lance)与[推理预设代码](https://github.com/bytedance/Lance/blob/main/data/datasets_custom/validation_dataset.py)，并对本地官方BucketResize.init_buckets做AST提取、标准库算术复算。官方描述已发布模型的视频训练达到480p、12FPS；代码存在video_192p/360p/480p，不应把可手动改尺寸称为官方已验收720p/1080p。图像预设另有image_256res/512res/768res，不等于相同像素级别的视频训练质量保证。

video_192p对应VAE面积参数256、ViT224；video_360p对应VAE480、ViT476；video_480p对应VAE640、ViT616。我们现行训练使用VAE480、ViT448，是自有组合，不是完整照搬官方360p预设。

BucketResize中的resolution R定义近似面积R²，实际桶由宽高比与16对齐的候选中选取，面积不是严格上界，也不是长边/短边固定R。以下为VAE训练/编辑bucket计算值，全部以**宽×高**书写（与前文形状表H×W记法不同，避免混读）：

| 比例 | video_192p / R256 | video_360p / R480 | video_480p / R640 |
| --- | --- | --- | --- |
| 21:9 | 368×160 | 752×320 | 976×416 |
| 16:9 | 336×192 | 624×352 | 848×480 |
| 4:3 | 304×224 | 560×416 | 752×560 |
| 1:1 | 256×256 | 480×480 | 640×640 |
| 3:4 | 224×304 | 416×560 | 560×752 |
| 9:16 | 192×336 | 352×624 | 480×848 |

按原视频比例选最近bucket，执行中心裁剪/缩放。不能把VAE预处理的624×352与后续VAE latent的39×22混为一谈。ViT另外还要28对齐，不能直接套上表作为ViT尺寸。

官方[Gradio设置](https://github.com/bytedance/Lance/blob/main/common/gradio_utils/settings.py)另有文生视频等使用的固定尺寸映射，例如360p的16:9是640×352、480p的4:3是736×560；它与训练/编辑BucketResize结果不完全相同。判断实际编辑输出应跟随真实预处理/target构建路径，不能仅凭预设名字或GUI文字推断。

现有multiturn/sequence_builder.py::_prepare_target_size在编辑时将target的帧数/H/W设为condition_tensor的T/H/W。因此决定原生输出尺寸的是source的VAE预处理结果以及构造的target噪声latent：latent空间每边乘16得到输出像素尺寸。VAE stride当前固定16，不因选择bucket而改变。文本生成入口可显式设置目标H/W，不能将该规则直接套用到编辑入口。

影响因素要区分：

- 输出像素宽高：目标latent网格、VAE解码倍率；当前编辑通路通过source的VAE变换及比例间接确定。
- 实际细节/质量：训练目标规格、素材细节、模型能力、source/reference信息与任务难度；提高输出像素数不保证增加真实细节。
- ViT与额外参考VAE尺寸：影响条件信息、质量及计算，独立于输出网格，不直接限制输出像素尺寸。
- 显存/token/位置范围：限制哪些组合可运行，但当前bucket不会因视频变长自动换低分辨率。

长视频的源/目标VAE开销示例（使用拟定12FPS、4k+1口径；是明确帧数的算术，实际采样器取整/crop需另查）：

| 约定时长与采样帧数 | 624×352源＋目标VAE | 848×480源＋目标VAE |
| --- | ---: | ---: |
| 5秒 / 61帧 | 27456 | 50880 |
| 10秒 / 121帧 | 53196 | 98580 |
| 20秒 / 241帧 | 104676 | 193980 |

以上不含ViT、当前参考、文字。例子中10秒480p光source/target已超过当前65536预算；20秒即使360p也超。固定总帧数覆盖更长时间可以保持token，但会降低时间分辨率，采样/输出fps必须一致描述真实时长，不能把动作加速或把长片独立缩成短片。

现行GT profile为max_num_frames=121、max_duration_seconds=6，旧CoinVE共同5秒窗另有数据合同。新数据文件变长不会自动建立正确长视频训练支持；还需核对采样窗口/取整、时间位置编码容量、总pack预算、输出帧率与实际显存。当前通用推理采样器assert_seconds=false的取整与旧配对数据采样路径不同，不能只用秒数推断实际F；实施时以处理后张量与采样时间戳验收。

本次仅核对与记录，不改变现有分辨率、时间规格或训练配置。
